Implements **SPEC §7.25.1** (the recall index) and **§7.25.2** (the drift

## 0. Read this first — three facts that shape every step

**1. The suite empties the database, so `psql` inspection needs provisioning.**
`internal/database/testutil/testutil.go` calls `pgDropAll` on entry to every
package and drops the database on exit. After any `make it` run the database has
**0 tables** and `psql` reports `relation "scenes" does not exist`. That is the
harness cleaning up, not a broken schema. Provision a scratch database before
inspecting anything (recipe in §1).

**2. `sqlc` and `golangci-lint` are NOT on `PATH`.** They live in `~/go/bin`.
Every codegen step below needs:

```bash
export PATH="$HOME/go/bin:$PATH"
sqlc version      # v1.29.0
```

**3. `internal/queries/*.sql.go` is generated. Never hand-edit it.**
`internal/queries/scene.sql.go` line 1 reads `// Code generated by sqlc. DO NOT
EDIT.` The source of truth is `internal/queries/sql/scene.sql`, and the
generated file is rewritten by `sqlc generate`. A hand-edited `.sql.go` is
silently reverted by the next `make generate`, and a reviewer reading the diff
sees generated code.

**The finding that shapes this plan.** `scene_tags` has no trigger. `scenes`,
`studios`, `performers` and `scene_performers` all fire into `upsert_scene_search`
or `upsert_tag_search`; `scene_tags` fires nothing. So adding a `tag_names`
column to `scene_search` *without* adding a trigger would produce an index that
silently reports whatever the last unrelated scene write happened to recompute —
worse than no column at all, because it looks populated.

## 3. Step 1 — the recall index (SPEC §7.25.1)

### 3.1 Files

### 3.2 The migration, complete

```sql
-- SPEC §7.25.1: make scene.details, scene.director and scene TAGS searchable.
--
-- scene_search has been rebuilt three times -- migrations 35 (tsvector), 56
-- (ParadeDB BM25) and 61 (the alias arrays) -- and none of them added these
-- three fields. They are where broad-stroke recall lives: `details` is free
-- text ("hotel room, rainy night"), `director` is a half-remembered-name cue,
-- and a tag name is the single most common thing a person remembers about a
-- scene they cannot place.
--
-- This migration is ADDITIVE. It does not rebuild the table: migration 61
-- DROPs and re-CREATEs it, and doing that again would drop the indexes and
-- rebuild every row for no reason when three columns and three index fields are
-- all that is needed.
--
-- The tag trigger is the load-bearing part. scene_tags has carried NO trigger
-- since 01_initial, so nothing has ever recomputed a scene's search row when
-- its tags changed. Without the statement-level triggers below, tag_names would
-- be correct only for scenes that happened to be written after the fact.

ALTER TABLE scene_search
    ADD COLUMN IF NOT EXISTS scene_details TEXT,
    ADD COLUMN IF NOT EXISTS scene_director TEXT,
    ADD COLUMN IF NOT EXISTS tag_names TEXT[];

-- Rebuild every existing row from the base tables. The scene_search rows that
-- exist now were built by migration 61's upsert, which never had these fields.
UPDATE scene_search ss
SET scene_details = S.details,
    scene_director = S.director,
    tag_names = COALESCE(tags.agg, '{}')
FROM scenes S
LEFT JOIN (
    SELECT ST.scene_id, ARRAY_AGG(DISTINCT T.name) AS agg
    FROM scene_tags ST JOIN tags T ON T.id = ST.tag_id
    GROUP BY ST.scene_id
) tags ON tags.scene_id = S.id
WHERE ss.scene_id = S.id;
```

Then the index. **The BM25 index must be dropped and recreated** — ParadeDB
requires every indexed column in the `USING bm25` list:

```sql
DROP INDEX IF EXISTS scene_search_bm25_idx;

CREATE INDEX scene_search_bm25_idx ON scene_search
USING bm25 (
    scene_id,
    scene_title,
    scene_date,
    studio_name,
    network_name,
    studio_aliases,
    network_aliases,
    performer_names,
    scene_code,
    scene_details,
    scene_director,
    tag_names
)
WITH (
    key_field='scene_id',
    text_fields='{
        "performer_names": {"fieldnorms": false, "record": "basic"},
        "studio_aliases": {"fieldnorms": false, "record": "basic"},
        "network_aliases": {"fieldnorms": false, "record": "basic"},
        "tag_names": {"fieldnorms": false, "record": "basic"}
    }'
);
```

Then `upsert_scene_search` must write the three new columns, or the next scene
write silently blanks them. **This is the part that is easy to miss and that
makes the whole feature a no-op if omitted:**

```sql
CREATE OR REPLACE FUNCTION upsert_scene_search(sid UUID) RETURNS VOID AS $$
BEGIN
    DELETE FROM scene_search WHERE scene_id = sid
        AND EXISTS (SELECT 1 FROM scenes WHERE id = sid AND deleted = true);

    INSERT INTO scene_search (scene_id, scene_title, scene_date, studio_name,
        network_name, studio_aliases, network_aliases, performer_names,
        scene_code, scene_details, scene_director, tag_names)
    SELECT S.id, S.title, S.date::TEXT, T.name, TP.name,
           COALESCE(ARRAY_AGG(DISTINCT SA.alias) FILTER (WHERE SA.alias IS NOT NULL), '{}'),
           COALESCE(ARRAY_AGG(DISTINCT NA.alias) FILTER (WHERE NA.alias IS NOT NULL), '{}'),
           COALESCE(ARRAY_AGG(DISTINCT P.name) FILTER (WHERE P.name IS NOT NULL), '{}') ||
           COALESCE(ARRAY_AGG(DISTINCT PS."as") FILTER (WHERE PS."as" IS NOT NULL), '{}'),
           S.code,
           S.details,
           S.director,
           COALESCE(ARRAY_AGG(DISTINCT TG.name) FILTER (WHERE TG.name IS NOT NULL), '{}')
    FROM scenes S
    LEFT JOIN scene_performers PS ON PS.scene_id = S.id
    LEFT JOIN performers P ON PS.performer_id = P.id
    LEFT JOIN studios T ON T.id = S.studio_id
    LEFT JOIN studio_aliases SA ON SA.studio_id = T.id
    LEFT JOIN studios TP ON T.parent_studio_id = TP.id
    LEFT JOIN studio_aliases NA ON NA.studio_id = TP.id
    LEFT JOIN scene_tags ST ON ST.scene_id = S.id
    LEFT JOIN tags TG ON TG.id = ST.tag_id
    WHERE S.id = sid AND S.deleted = false
    GROUP BY S.id, T.name, TP.name
    ON CONFLICT (scene_id) DO UPDATE SET
        scene_title = EXCLUDED.scene_title, scene_date = EXCLUDED.scene_date,
        studio_name = EXCLUDED.studio_name, network_name = EXCLUDED.network_name,
        studio_aliases = EXCLUDED.studio_aliases, network_aliases = EXCLUDED.network_aliases,
        performer_names = EXCLUDED.performer_names, scene_code = EXCLUDED.scene_code,
        scene_details = EXCLUDED.scene_details,
        scene_director = EXCLUDED.scene_director,
        tag_names = EXCLUDED.tag_names;
END;
$$ LANGUAGE plpgsql;
```

Then the triggers. **Statement-level, matching the shape already proven at
`56_paradedb_search.up.sql:130-146`** — a row-level trigger would fire the
upsert once per tag per scene, which on a bulk import is thousands of rewrites
of the same row:

```sql
CREATE OR REPLACE FUNCTION trg_scene_tags_inserted() RETURNS TRIGGER AS $$
BEGIN
    PERFORM upsert_scene_search(scene_id)
    FROM (SELECT DISTINCT scene_id FROM new_rows) affected;
    RETURN NULL;
END;
$$ LANGUAGE plpgsql;
CREATE TRIGGER trg_scene_search_on_st_insert
AFTER INSERT ON scene_tags
REFERENCING NEW TABLE AS new_rows
FOR EACH STATEMENT EXECUTE FUNCTION trg_scene_tags_inserted();

CREATE OR REPLACE FUNCTION trg_scene_tags_deleted() RETURNS TRIGGER AS $$
BEGIN
    PERFORM upsert_scene_search(scene_id)
    FROM (SELECT DISTINCT scene_id FROM old_rows) affected;
    RETURN NULL;
END;
$$ LANGUAGE plpgsql;
CREATE TRIGGER trg_scene_search_on_st_delete
AFTER DELETE ON scene_tags
REFERENCING OLD TABLE AS old_rows
FOR EACH STATEMENT EXECUTE FUNCTION trg_scene_tags_deleted();
```

One more, and this is the one that closes the loop: **a tag's own rename must
reach every scene carrying it.** `tags` already has `trg_tag_search_on_tag`
into `upsert_tag_search`, so the tag row is updated but the scenes are not:

```sql
CREATE OR REPLACE FUNCTION trg_tag_renamed_scenes() RETURNS TRIGGER AS $$
BEGIN
    PERFORM upsert_scene_search(ST.scene_id)
    FROM scene_tags ST
    WHERE ST.tag_id = NEW.id;
    RETURN NULL;
END;
$$ LANGUAGE plpgsql;
CREATE TRIGGER trg_scene_search_on_tag_rename
AFTER UPDATE OF name ON tags
REFERENCING NEW TABLE AS new_rows
FOR EACH STATEMENT EXECUTE FUNCTION trg_tag_renamed_scenes();
```

### 3.3 The `.down.sql`

Reverse in dependency order — triggers, then the function, then the index, then
the columns. Note the `UPDATE` that populates the new columns is **not
reversible**, and that is stated rather than hidden:

```sql
-- SPEC §7.25.1 down. The backfill's DATA is not recoverable by dropping the
-- columns -- it is, because every value is derived from scenes/scene_tags/tags
-- and is recomputed by upsert_scene_search on the next scene write. Nothing is
-- lost that the next write would not rebuild.

DROP TRIGGER IF EXISTS trg_scene_search_on_tag_rename ON tags;
DROP FUNCTION IF EXISTS trg_tag_renamed_scenes();

DROP TRIGGER IF EXISTS trg_scene_search_on_st_insert ON scene_tags;
DROP TRIGGER IF EXISTS trg_scene_search_on_st_delete ON scene_tags;
```

### 3.4 The query change

`internal/queries/sql/scene.sql`, the `SearchScenes` body. Add three disjuncts
to **both** arrays, and per SPEC §7.25.1 R1 weight tags above studio in the
relevance array only:

```sql
            paradedb.match(field => 'scene_details', value => tok),
            paradedb.match(field => 'scene_director', value => tok),
            paradedb.match(field => 'tag_names', value => tok),
```

Relevance array, tags boosted above studio's unboosted 1.0:

```sql
            paradedb.boost(factor => 2.0, query => paradedb.match(field => 'tag_names', value => tok)),
            paradedb.match(field => 'scene_details', value => tok),
            paradedb.match(field => 'scene_director', value => tok),
```

Do **not** touch the coverage array's weights. The flat `10000.0` per matched
token is what makes "matches more of the query" outrank "matches more strongly",
and raising a field's relevance weight changes only ordering *within* a tier.

## 4. Step 2 — the drift check (SPEC §7.25.2)

### 4.1 The query

New file `internal/queries/sql/scene.sql` addition:

```sql
-- name: CountSceneSearchDrift :one
-- SPEC §7.25.2. scene_search is maintained by triggers, so a scene whose
-- trigger did not fire is invisible to every search, permanently, and nothing
-- in the product notices.
--
-- Two numbers, because they answer different questions: the counts answer
-- "is anything wrong", the id list answers "what". A count that matches while
-- the SETS differ is not possible here -- scene_search has a PRIMARY KEY on
-- scene_id and one row per scene -- but the ids are returned anyway, because a
-- diagnosis you have to re-derive from a count is a second query somebody will
-- forget to write.
SELECT
    (SELECT COUNT(*) FROM scenes WHERE deleted = false)                AS scene_count,
    (SELECT COUNT(*) FROM scene_search)                              AS indexed_count,
    COALESCE((
        SELECT ARRAY_AGG(s.id) FROM scenes s
        WHERE s.deleted = false
          AND NOT EXISTS (SELECT 1 FROM scene_search ss WHERE ss.scene_id = s.id)
    ), '{}')                                                         AS missing_ids;
```

### 4.2 The Go surface

`internal/service/scene/` — add a `SearchDrift` struct and a `Drift(ctx)`
method. Follow the package's existing receiver style; the service is
`(*Scene)` with a `queries *queries.Queries`.

```go
// Drift reports scenes that are absent from scene_search.
//
// SPEC §7.25.2. The index is trigger-maintained and has no way to report a row
// it missed, so this is the only way a missed row is ever visible.
type Drift struct {
	SceneCount  int32       `json:"scene_count"`
	IndexedCount int32      `json:"indexed_count"`
	MissingIDs  []uuid.UUID `json:"missing_ids"`
}

// Drifted reports whether the two counts disagree.
func (d Drift) Drifted() bool { return d.SceneCount != d.IndexedCount }
```

## 5. Step 3 — the integration test that proves the recall works

Without this the feature is a schema change with no observable behaviour.

`internal/api/scene_search_recall_integration_test.go`:

1. Create a scene with `details` = `'a cramped hotel room on a rainy night'` and
   `code` = `NULL`, `title` = `'Untitled'`.
2. Assert `scene_search` has a row for it **whose `tag_names` is empty** — the
   pre-feature state had no such column, so this also pins the new shape.
3. Add two tags to it. **Assert `tag_names` is now populated**, which is the
   assertion that fails if the `scene_tags` trigger is missing.
4. Rename one tag. **Assert `tag_names` reflects the new name** — the assertion
   that fails if `trg_scene_search_on_tag_rename` is missing.
5. Update the scene's `details`. Assert `scene_details` followed.
6. Run `SearchScenes` with the token `'rainy'` and assert the scene is returned.
   This is the end-to-end proof.
7. Run `Drift` and assert `Drifted() == false` after all of the above.

**Gate, in this order:**

```bash
export POSTGRES_DB='postgres:smoke_pw@127.0.0.1:55434/stash-box-test?sslmode=disable'
go test -tags=integration -count=1 -p 1 ./internal/api/ -run TestSceneSearchRecall -v
```

Expected: every subtest PASS.

**Then prove the test can fail — remove the `scene_tags` trigger and re-run:**

```sql
DROP TRIGGER trg_scene_search_on_st_insert ON scene_tags;
```

Expected: step 3 fails. Restore it. **A test that cannot fail is not evidence
that the trigger works.**

## 7. Definition of done

- [ ] Migration 103 exists with **both** halves. An up with no down makes the
      chain one-directional and a rollback does not exist.
- [ ] `scene_search` carries `scene_details`, `scene_director`, `tag_names`.
- [ ] The BM25 index lists all twelve fields.
- [ ] `upsert_scene_search` writes all three — **the single most-skippable step.**
- [ ] Four triggers exist: `scene_tags` insert, `scene_tags` delete, `tags`
      rename. (Three functions, four triggers — the rename trigger and the
      delete trigger are separate objects.)
- [ ] `SearchScenes` matches all three new fields in both arrays.
- [ ] `sqlc generate` produces a diff only in `scene.sql.go`.
- [ ] `10000.0` appears exactly once in the generated file.
- [ ] The drift query exists and its test **fails when the query is broken**.
- [ ] The integration test fails with the `scene_tags` trigger dropped.
- [ ] `make it` green.
- [ ] No `internal/database/migrateprobe/` left behind.
- [ ] A down-migration rehearsal: apply 103, revert it, re-apply it, and confirm
      the schema returns to the 9-column shape and comes back. **A `.down.sql`
      that has never been run is a claim, not a teardown.**

## 8. What this plan does NOT build

Named so the next agent does not re-derive it:

- **No ML, no CLIP, no image hashes, no embeddings.** SPEC §7.25.7.
- **No trigram fallback tier.** The GIN trgm indexes exist (migrations 73/75) and
  no live query uses them. That is real and it is cheap, but it is a *ranking*
  change with its own measurement question, not part of making the fields
  findable. It belongs after the evaluation set exists.
- **No date range, duration band or performer count filter** — SPEC §7.25.4,
  a separate plan.
- **Nothing on the identification board** — SPEC §7.25.3, a separate plan.
- **No federation.** SPEC §7.25.7; D2 is complete but a new question *kind* is
  Phase 4.
- **No auto-resolution of anything.** SPEC §7.25.3.
