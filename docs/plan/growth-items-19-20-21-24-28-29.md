# PLAN — growth items 19, 20, 21, 24, 28, 29

Implements `docs/spec/growth-items-19-20-21-24-28-29.md`. Detailed enough to implement
without asking questions. Every symbol below was verified against the tree before being
written down; the verification notes say which.

## Order, and why

**29 → 24 → 21 → 19 → 28 → 20.** Cheapest and most-settled first, so each milestone
teaches the next one something.

- **29 first** because the service layer, queries and integration test already exist.
  It is pure wiring, and it establishes the shape every later item follows: GraphQL type
  → resolver delegating to a service that already owns the logic → live assertion script.
- **24 second** because it extends an existing table rather than creating one, so it
  reuses 29's wiring pattern on a table that already has a GraphQL type.
- **21 third** because it is the first item needing a genuinely new *derived* query
  (a timeline bucketed by year), and it is also the first needing a new migration-free
  aggregate query. Doing it after 29 and 24 means the query patterns are familiar.
- **19 fourth** because it is a one-line semantic addition to an existing switch, and it
  needs a correctness argument about pagination that benefits from the query experience
  the previous three built.
- **28 fifth** because it is the first item creating a **table** and the first with a
  state machine and an authorization decision, and the last item that should touch the
  database before the frontend workstream.
- **20 last** because it is pure frontend, touches no backend, and its verification is
  visual. It cannot break the five backend items, so isolating it last means a styling
  problem cannot masquerade as a data problem.

**The hard ordering constraint is only the last step of every item:** `frontend` build
must precede `go build`, because `frontend/embed.go` is `//go:embed build`. Getting this
wrong ships a blank SPA with HTTP 200 and no console error.

### 29.1 — the GraphQL schema

New file `graphql/schema/types/review.graphql`:

```graphql
"""
A structured review of a performer or studio.

`rating` is nullable ON PURPOSE: a review with a body and no rating is a legitimate
thing to write, and a schema that required a rating would force people to invent one.
The rating pointer is what makes that expressible.
"""
type Review {
  id: ID!
  author: User!
  entityType: ReviewEntityTypeEnum!
  entityId: ID!
  "Null when the reviewer wrote prose without a numeric rating."
  rating: Int
  body: String
  "Set by the system, not the author: whether the reviewer is a known contributor."
  verified: Boolean!
  status: ReviewStatusEnum!
  createdAt: Time!
  updatedAt: Time!
}

enum ReviewEntityTypeEnum {
  PERFORMER
  STUDIO
}

enum ReviewStatusEnum {
  "Visible to everyone who can read."
  PUBLISHED
  "Written but hidden: author-only, or awaiting moderation."
  PENDING
  "Rejected or spam. Kept for the author to read, never listed."
  REJECTED
}

"A review plus the aggregate a client renders next to it."
type ReviewSummary {
  average: Float
  count: Int!
}
```

Then add to the existing performer and studio types:

```graphql
extend type Performer {
  reviews(perPage: Int = 25, page: Int = 1): [Review!]! @hasRole(role: READ)
  reviewSummary: ReviewSummary! @hasRole(role: READ)
}
```

…and the equivalent on `Studio`. **Verify the `@hasRole` directive name against

## Item 24 — nesting on the existing category layer

**Verified:** `tag_categories(id, group, name, description, created_at, updated_at)`,
**0 rows**. `TagCategory` type exists in `graphql/schema/types/tag.graphql` with
`id, name, group, description` and `TagCategoryCreateInput`. `tags.category_id` exists
and tag queries filter on it. No `parent_id` column, and `information_schema` confirms
zero `%parent%`/`%hierarch%` columns on any `%tag%` table.

**The design question:** should nesting be a `parent_id` self-reference, or a separate
level column?

**Decision: `parent_id` self-reference with a depth guard.** A level column would permit
inconsistent data (a level-2 tag whose parent is a level-3 tag) and would make moving a
subtree a bulk UPDATE. A self-reference expresses the actual relation and lets the
database refuse the cycles.

### 24.1 — migration

`internal/database/migrations/postgres/106_tag_category_nesting.up.sql`:

```sql
-- Nesting for tag categories (SPEC §7, growth item 24).
--
-- The category layer ALREADY EXISTED (id, group, name, description) with a GraphQL
-- type and create/update mutations -- and zero rows. So this is not a vocabulary
-- project; the mechanism was built and never used. What it lacked was any way to say
-- that one category is a child of another.
--
-- SELF-REFERENCE, NOT A LEVEL COLUMN. A `level int` would allow a level-2 category
-- whose parent is a level-3 one, and moving a subtree would be a bulk UPDATE with no
-- way to check it. A parent_id expresses the actual relation, and the trigger below
-- makes a cycle impossible rather than merely unlikely.
ALTER TABLE tag_categories
  ADD COLUMN IF NOT EXISTS parent_id uuid REFERENCES tag_categories(id) ON DELETE SET NULL;

CREATE INDEX IF NOT EXISTS tag_categories_parent_id_idx ON tag_categories(parent_id);

-- Refuse a cycle. A recursive CTE walks upward from the proposed parent; if it reaches
-- the row being updated, the move would create a cycle and is rejected.
--
-- The guard is on INSERT and UPDATE OF parent_id, and it compares ids so it also stops
-- a category being made its own parent.
CREATE OR REPLACE FUNCTION tag_categories_no_cycle()
RETURNS trigger LANGUAGE plpgsql AS $$
BEGIN
  IF NEW.parent_id IS NULL THEN
    RETURN NEW;
  END IF;
  IF NEW.parent_id = NEW.id THEN
    RAISE EXCEPTION 'tag category % cannot be its own parent', NEW.id;
  END IF;
  IF EXISTS (
    WITH RECURSIVE ancestors AS (
      SELECT id, parent_id FROM tag_categories WHERE id = NEW.parent_id
      UNION ALL
      SELECT c.id, c.parent_id
        FROM tag_categories c
        JOIN ancestors a ON c.id = a.parent_id
    )
    SELECT 1 FROM ancestors WHERE id = NEW.id
  ) THEN
    RAISE EXCEPTION 'tag category % would create a cycle', NEW.id;
  END IF;
  RETURN NEW;
END;
$$;

DROP TRIGGER IF EXISTS tag_categories_no_cycle_trg ON tag_categories;
CREATE TRIGGER tag_categories_no_cycle_trg
  BEFORE INSERT OR UPDATE OF parent_id ON tag_categories
  FOR EACH ROW EXECUTE FUNCTION tag_categories_no_cycle();
```

Down migration `106_tag_category_nesting.down.sql` drops the trigger, the function and
the column.

> **Verification note.** `recursive CTE inside EXISTS` is valid in Postgres, but run
> `scripts/verify-106.sh` immediately after applying. If it errors, the fallback is to
> hoist the CTE into its own statement — the *semantics* are what matter, and the
> trigger must be proven to reject a cycle, not assumed to.

### 24.2 — queries

Add to `internal/queries/sql/tag.sql`:

- `FindTagCategoryDescendants(id)` — recursive CTE downward, with a depth column.
- `FindTagCategoryAncestors(id)` — recursive CTE upward.

## Item 21 — performer timeline

**Verified:** `performers` has `career_start_year`, `career_end_year` and **no**
per-scene history table. `scenes.date` is the only usable date; 13 of 16 live scenes
have one, ranging 2016-04-01 to 2022-08-08. There is no `performer_history` table.

**Decision: derive from `scenes.date`, bucketed by year.** A performer timeline is the
story of when someone was working, and the schema's only evidence of that is when their
scenes are dated. `career_start_year`/`career_end_year` are user-entered bounds and are
frequently empty; they cannot be the spine of a timeline.

**Undated scenes are the interesting case.** 3 of 16 have no date. They must be counted
and surfaced as an explicit `undated_count`, never silently dropped: a timeline that
quietly omits a fifth of the archive reads as complete when it is not.

### 21.1 — query

Add `internal/queries/sql/performer_timeline.sql`:

```sql
-- name: FindPerformerTimeline :many
-- Year buckets of a performer's appearances (growth item 21).
--
-- DERIVED FROM scenes.date, NOT FROM career_start_year/career_end_year. Those two are
-- user-entered bounds and are frequently empty; scenes.date is the only date the
-- schema actually has about when someone was working. Bucketing by year rather than
-- listing every scene is what makes it a TIMELINE: the shape is the point.
--
-- UNDATED SCENES ARE COUNTED, NOT DROPPED. A scene with a NULL date is real work by
-- this performer that cannot be placed. Silently excluding it would make the timeline
-- claim a completeness it does not have, so it is surfaced as its own bucket.
SELECT
    -- The year, or NULL for undated. A NULL year is meaningful, not missing data.
    substr(scenes.date, 1, 4) AS year,
    count(*)::int AS scene_count,
    count(DISTINCT scenes.studio_id)::int AS studio_count
FROM scenes
JOIN scene_performers ON scene_performers.scene_id = scenes.id
WHERE scene_performers.performer_id = $1
  AND NOT scenes.deleted
GROUP BY 1
ORDER BY 1 NULLS LAST;
```

`ORDER BY 1 NULLS LAST` puts undated last rather than first, because an undated bucket
sorting to the top would be read as the most recent year.

### 21.2 — service and resolver

`internal/service/performer/timeline.go` with `Timeline(ctx, id)`, returning year buckets
plus a summary (first year, last year, total scenes, undated count). The resolver exposes
it on `Performer` as `timeline`.

### 21.3 — verification

Integration test asserting: buckets are in ascending year order; the undated bucket is
present and last when undated scenes exist; a performer with no scenes returns an empty
list and **not** an error; the scene counts sum to the performer's total appearance count
including undated.

Live script `scripts/verify-performer-timeline.sh`, then read the timeline on a real
performer page.

## Item 19 — random scene sort

**Verified:** `SceneSortEnum` in `graphql/schema/types/scene.graphql` line 229 contains
`TITLE, DATE, DURATION, TRENDING, POPULARITY, CREATED_AT, UPDATED_AT` — **no RANDOM**.
Sorting is a `switch input.Sort` in `internal/service/scene/query.go` line ~281, with
`POPULARITY` and `TRENDING` as explicit cases and a `default:` that lowercases the enum
name into `scenes.<field>`.

**The correctness argument that matters.** The `default:` branch would turn `RANDOM` into
`scenes.random ASC`, which does not exist. So `RANDOM` needs its own case. And the
secondary sort must not be a stable tiebreak on `id`: with `ORDER BY random()` every row
has a distinct key, so pagination is genuinely random per request — which is the desired
behaviour, but it must be *said*, because it means page 2 does not continue page 1.

```go
case models.SceneSortEnumRandom:
    if !forCount {
        // random() gives every row a distinct sort key, so this is a genuinely random
        // PAGE rather than a random ordering that pagination then truncates
        // deterministically: page 2 will NOT continue page 1, and will not repeat
        // page 1's rows. That is the intent of a random sort, but it is also why it
        // cannot be combined with a stable secondary key without making the randomness
        // a lie.
        query = query.OrderBy("random()")
        query = queryhelper.ApplyPagination(query, input.Page, input.PerPage)
    }
```

### 19.1 — schema

Add `RANDOM` to `SceneSortEnum` with a doc comment stating the pagination property above.

### 19.2 — frontend

Add to the sort control in `frontend/src/pages/scenes/` so the option is reachable, and
add the label to the translation file.

### 19.3 — verification

Integration test: two consecutive `sort: RANDOM` queries over a fixture of at least 30
scenes must not return the identical ordering (assert the orderings differ, with a
retries loop because 30! orderings make a false failure vanishingly unlikely but not
impossible). Also: `RANDOM` must work **with** a filter applied — the tempting bug is
implementing it in the `default:` branch, which ignores filters.

Live script asserting two HTTP calls return different scene ids.

## Item 28 — shareable lists

**Verified:** no `*List*` table exists. The closest existing thing is
`performer_favorites(performer_id, user_id, created_at)` — per-user, and therefore
already private by construction.

### 28.1 — migration

`107_shareable_lists.up.sql`: `shareable_lists(id, owner_id, name, description,
visibility, published_at, created_at, updated_at)` and
`shareable_list_items(id, list_id, entity_type, entity_id, position, created_at)`.

`visibility` in `('PRIVATE','UNLISTED','PUBLIC')`. The state machine: **a list is
`PRIVATE` on creation and stays private until its owner explicitly publishes it.**
`UNLISTED` means reachable by direct link but absent from listings.

The audit trail is the reason this is safe to ship without a moderation queue: every
publication records `published_at`, so "who made this public and when" is answerable
from the row itself.

### 28.2 — GraphQL

`Query.shareableLists`, `Query.shareableList(id)`,
`Mutation.shareableListCreate/Update/Publish/Unpublish/Delete`,
`Mutation.shareableListItemAdd/Remove/Reorder`. Authorization: mutations require
ownership; reading a `PRIVATE` list requires ownership; `PUBLIC` requires `READ`.

### 28.3 — verification

Integration test asserting the state machine, which is the whole point: a newly created
list is **not** visible to another user; after `Publish` it is; after `Unpublish` it is
not again; a non-owner cannot publish or unpublish; a `PRIVATE` list returns an error for
a non-owner rather than an empty result (silently returning empty would make a private
list look deleted).

## Item 20 — theme foundation and responsive baseline

**Verified:** `frontend/src/styles/theme.scss` is a dark-only palette:
`--bs-body-bg: #202b33`, `$text-color: #f5f8fa`, `.card { background-color: #30404d }`,
`.modal &-header { background-color: #30404d }`. Across 33 stylesheets: **zero**
`@media` queries, **zero** occurrences of `prefers-color-scheme`, `data-theme`,
`ThemeProvider` or `useTheme`. Dependencies are React 18 + `bootstrap` + `react-bootstrap`.

### 20.1 — the token layer

New `frontend/src/styles/tokens.scss`, imported **before** `theme.scss` in `App.scss`.
Every hardcoded colour in `theme.scss` becomes a custom property, so both palettes are
defined in one place:

```scss
// Design tokens. Every colour the app uses resolves to one of these, so a theme is a
// value change rather than a stylesheet rewrite.
//
// THE APP WAS DARK-ONLY. theme.scss hardcoded #202b33, #30404d and #f5f8fa, so
// "add dark mode" would have meant adding a second palette to a codebase with one.
// This defines both and leaves the per-component colours for the follow-on.
:root {
  --sb-bg: #f5f8fa;
  --sb-surface: #ffffff;
  --sb-text: #182026;
  --sb-muted: #5c7080;
  --sb-border: rgba(24 32 38 / 12%);
}

:root[data-theme="dark"] {
  --sb-bg: #202b33;
  --sb-surface: #30404d;
  --sb-text: #f5f8fa;
  --sb-muted: #bfccd6;
  --sb-border: rgba(16 22 26 / 40%);
}
```

### 20.2 — the switch

`frontend/src/contexts/ThemeContext.tsx` — `ThemeProvider` with
`"system" | "light" | "dark"`, defaulting to `system`, persisted to `localStorage`
under `sb.theme`, applied by setting `document.documentElement.dataset.theme`. `system`
subscribes to `matchMedia("(prefers-color-scheme: dark)")` and follows it, which is what
makes the default correct for someone who has never opened the site.

A small `useTheme()` hook and a toggle in the navbar.

### 20.3 — responsive baseline

Because there are **zero** existing media queries, add a breakpoint scale as CSS custom
properties and apply it to the app shell, the navbar and the card grid. This is the
foundation, not full mobile parity — stated as such in the spec.

### 20.4 — verification

```bash
cd frontend && node node_modules/vitest/vitest.mjs run   # all pass
```

New `ThemeContext.test.tsx` asserting: the persisted choice wins over `system`; an unset
choice follows the OS; toggling sets `data-theme`; an unknown stored value falls back to
`system` rather than leaving the document unthemed.

**The manual check, which no test performs:** open the app in both themes and confirm
legibility. A stylesheet that compiles is not a page a human can read.
