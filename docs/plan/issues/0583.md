# #583 — password length limit (closed upstream as not-a-bug)

**Status: not a bug. Closed by the maintainer (erri120) in January 2023. No code
change was made.**

## The report

> The password length limit is supposed to be 64 but I've used a 50 character
> password and I've gotten an error. Perhaps it's checking for bits instead of
> characters, and some unicode characters may take more space than simple ascii
> characters.

## Why the code is correct

The limit is 64 **bytes**, deliberately:

- Go strings are byte sequences, and their length is in bytes.
- A multi-byte UTF-8 character (any character outside ASCII) occupies 2–4 bytes,
  so a 50-character password containing them can exceed 64 bytes.
- The password is converted to a byte array and handed to **bcrypt**, which takes
  a byte array and does not care about characters or runes. Limiting characters
  instead of bytes would allow an unbounded number of bytes into the hash, which
  is the thing that actually matters for cost and for bcrypt's 72-byte input
  truncation.

The maintainer's own summary in the thread: the code works as intended.

## The one defensible change, and why it was not made

erri120 also suggests changing the *message* so the limit is expressed in the
unit the code actually uses. That is a reasonable, low-risk improvement, and it
is the only thing here worth doing.

It is not implemented in this fork because the fix belongs in the upstream error
text, not in the validation logic, and changing validation to match a
misunderstanding would introduce the bug the maintainer explicitly warned about:

> If you change the message instead of the code you are going to end up allowing
> some passwords with more characters than the limit when they use ascii, which
> would also be a bug.
