# SPEC — growth items 19, 20, 21, 24, 28, 29

Six items, one spec, written before any code. Four of the six were marked `[!]` in
`docs/track/TRACK-growth-tiers-1-2.md`, meaning "its own project". The owner has asked
for all of them, so each is scoped here to something genuinely completable, and the
scoping decision is stated rather than assumed.

**Two tracker claims are wrong**, and writing this spec is what caught them:

- **Item 24** says "no — vocabulary project". A `tag_categories` table **exists**, with
  `id, group, name, description`, a full `TagCategory` GraphQL type, create/update
  mutations, and a `category_id` filter on tag queries. The category layer is built. It
  has **zero rows** and no nesting. So the work is not the vocabulary — it is making
  the existing layer useful and adding the one level of nesting the schema lacks.
- **Item 29** says "**no review GraphQL type exists at all**" and reads as a build-from-
  scratch. A `reviews` table exists with `author_id, entity_type, entity_id, rating,
  body, verified, status`; there are **11 sqlc queries** (`CreateReview`, `ListReviewsForEntity`,
  `GetReviewAverage`, `SetReviewStatus`, …), a service package, unit tests, and an
  integration test. Only the **GraphQL surface is missing**. This is the cheapest item
  on the list by a wide margin.

### Item 20 is not "add dark mode"

`frontend/src/styles/theme.scss` hardcodes a dark palette: `--bs-body-bg: #202b33`,
`.card { background-color: #30404d }`, `$text-color: #f5f8fa`, and 33 stylesheets with
**zero** `@media` queries and zero `prefers-color-scheme` / `data-theme` / `ThemeProvider`
anywhere. The application is dark-only, not theme-aware.

So "dark mode" would add a second palette to a codebase that has one, and "mobile"
would add breakpoints to a codebase that has none. Both are real work; both are large.
What ships instead is the **foundation**: a CSS-custom-property layer over the palette,
a `data-theme` attribute on `<html>`, a `ThemeContext` with system/light/dark and
persisted choice, and a responsive baseline. That is what makes both later, and it is
honest about being a foundation rather than claiming the workstream is finished.

### Item 28: why moderation is decided rather than deferred

A shareable list is public user-generated content, and publishing one is the
trust-sensitive action. The decision: **a list is private until its owner explicitly
publishes it, and publishing is itself auditable.** Creation and editing require
`WRITE` on the owner; reading a published list requires `READ`; unpublishing is always
available to the owner and to a moderator. No implicit publication, no silent
discovery of drafts. This is deliberately the smallest policy that makes the feature
safe — a full moderation queue is a separate project and is *not* claimed here.

## Non-goals, stated so they are not mistaken for omissions

- **No implicit publication** of lists (item 28) and **no moderation queue** — only the
  state machine and the audit trail.
- **No light-theme parity across all 33 stylesheets** (item 20). The token layer and the
  theme switch ship; the remaining per-component colours are the follow-on.
- **No performer credit-line history** (item 21). `scenes.date` is the only date the
  schema has; `performers` has `career_start_year`/`career_end_year` but no per-scene
  rows. Bucketing by year is the strongest timeline this schema supports.
- **No tag vocabulary authoring** (item 24). Creating good categories is curation work
  for a human; the mechanism is what ships.
- **No review editing by non-authors, no review-of-review** (item 29).

## The definition of done, as commands

Every item must satisfy these before it is called done:

```bash
export PATH="$HOME/.cargo/bin:$PATH"   # system rustc is broken on this host
cd /home/alvaro/code-local/go/stash-box

# 1. Backend compiles and unit tests pass (32 packages, 0 failures)
go build ./... && go test ./... 2>&1 | grep -cE '^(FAIL|--- FAIL)'   # → 0

# 2. Integration tests pass. THE DSN MATTERS: a wrong one runs the suite against
#    an EMPTY archive and every row-expecting assertion fails plausibly.

go test -tags=integration -count=1 -p 1 ./... 2>&1 | grep -E '^(FAIL|--- FAIL)'  # → empty

# 3. Frontend tests pass
cd frontend && node node_modules/vitest/vitest.mjs run 2>&1 | tail -5

# 4. Frontend BEFORE Go, or the SPA ships blank. frontend/embed.go is //go:embed build.
cd frontend && node node_modules/vite/bin/vite.js build
cd .. && go build -o /tmp/sbx ./cmd/stash-box
```

And each item carries its own live assertion script, because automated tests passing is
necessary and not sufficient: the deployed binary must actually serve the feature.

**The manual check no test performs:** open `http://127.0.0.1:9999/`, log in, and confirm
each new surface renders and reads correctly. Item 20 in particular is a *visual*
change, and a passing stylesheet build says nothing about whether the result is legible.
