# SPEC — growth items 19, 20, 21, 24, 28, 29

Six items, one spec, written before any code. Four of the six were marked `[!]` in
`docs/track/TRACK-growth-tiers-1-2.md`, meaning "its own project". The owner has asked
for all of them, so each is scoped here to something genuinely completable, and the
scoping decision is stated rather than assumed.

**Two tracker claims are wrong**, and writing this spec is what caught them:

- **Item 24** says "no — vocabulary project". A `tag_categories` table **exists**, with
  `id, group, name, description`, a full `TagCategory` GraphQL type, create/update
  mutations, and a `category_id` filter on tag queries. The category layer is built. It
  has **zero rows** and no nesting. So the work is not the vocabulary — it is making
  the existing layer useful and adding the one level of nesting the schema lacks.
- **Item 29** says "**no review GraphQL type exists at all**" and reads as a build-from-
  scratch. A `reviews` table exists with `author_id, entity_type, entity_id, rating,
  body, verified, status`; there are **11 sqlc queries** (`CreateReview`, `ListReviewsForEntity`,
  `GetReviewAverage`, `SetReviewStatus`, …), a service package, unit tests, and an
  integration test. Only the **GraphQL surface is missing**. This is the cheapest item
  on the list by a wide margin.

### Item 20 is not "add dark mode"

`frontend/src/styles/theme.scss` hardcodes a dark palette: `--bs-body-bg: #202b33`,
`.card { background-color: #30404d }`, `$text-color: #f5f8fa`, and 33 stylesheets with
**zero** `@media` queries and zero `prefers-color-scheme` / `data-theme` / `ThemeProvider`
anywhere. The application is dark-only, not theme-aware.

So "dark mode" would add a second palette to a codebase that has one, and "mobile"
would add breakpoints to a codebase that has none. Both are real work; both are large.
What ships instead is the **foundation**: a CSS-custom-property layer over the palette,
a `data-theme` attribute on `<html>`, a `ThemeContext` with system/light/dark and
persisted choice, and a responsive baseline. That is what makes both later, and it is
honest about being a foundation rather than claiming the workstream is finished.

### Item 28: why moderation is decided rather than deferred

A shareable list is public user-generated content, and publishing one is the
trust-sensitive action. The decision: **a list is private until its owner explicitly
publishes it, and publishing is itself auditable.** Creation and editing require
`WRITE` on the owner; reading a published list requires `READ`; unpublishing is always
available to the owner and to a moderator. No implicit publication, no silent
discovery of drafts. This is deliberately the smallest policy that makes the feature
safe — a full moderation queue is a separate project and is *not* claimed here.

## Non-goals, stated so they are not mistaken for omissions

- **No implicit publication** of lists (item 28) and **no moderation queue** — only the
  state machine and the audit trail.
- **No light-theme parity across all 33 stylesheets** (item 20). The token layer and the
  theme switch ship; the remaining per-component colours are the follow-on.
- **No performer credit-line history** (item 21). `scenes.date` is the only date the
  schema has; `performers` has `career_start_year`/`career_end_year` but no per-scene
  rows. Bucketing by year is the strongest timeline this schema supports.
- **No tag vocabulary authoring** (item 24). Creating good categories is curation work
  for a human; the mechanism is what ships.
- **No review editing by non-authors, no review-of-review** (item 29).

The lesson worth keeping: a script's comment is a claim, not evidence, and mine

running `sqlc generate` and reading an error, not reading the comment.

### 107's query layer

19 queries in `internal/queries/sql/list.sql`. Three choices worth stating:

- `CreateList` has no `published_at` column at all. A create that could publish
  would contradict the policy; omitting the column makes publication structurally a
  separate act rather than a discipline.
- `PublishList` is ONE statement carrying the actor, not an UPDATE followed by an
  INSERT into `list_audit`. A publication without its audit row is the state the
  policy forbids, and splitting the write makes it reachable on partial failure.
- `FindListsByIds` does NOT filter on `published_at`. Visibility is the caller's
  decision, made with the full row in hand, because a draft must stay
  distinguishable from a non-existent list -- a filter here would erase that.

`UnpublishList` is guarded on `published_at IS NOT NULL`, so unpublishing something
already private returns no rows rather than fabricating an unpublish event.

### Verification harness defects found while mutation-testing 107

Both are the same shape: a test that reports coverage it does not have.

1. `run ok` checked only that psql **exited zero**. Assertions written as

2. The script DELETED a user to prove the audit row survives and never CREATED one,
   so each run consumed a user. After a few runs the actor query found nobody and
   the case took its `skip` branch: reporting nothing, tallying 0 failed, claiming
   full coverage while exercising nothing. It now creates and removes its own two
   users, and a missing precondition is a FAIL rather than a skip.

Current state: 24 assertions, all load-bearing. Mutations verified to fail:
`published_by` CHECK weakened, entity-required CHECK dropped, duplicate-entity key
weakened, `owner_name` CHECK weakened, browse index made non-partial,
unique-name index dropped, `actor_id` switched to CASCADE.

### A schema change the mutation work forced

The unique key on `list_items` was `(list_id, entity_type, entity_id)`, which
permits one uuid to appear in a single list as both a SCENE and a PERFORMER. A
client resolving "item 3" then has two candidates and no rule to choose. Now
`(list_id, entity_id)`. Nil cost in practice: uuids are generated per table, so a
scene id is never a performer id. Found by a mutation that *passed* -- a test
insufficient to tell the right key from a wrong one is a real finding, not a
missing one.

### Item 28 frontend, and two bugs only a live server could find

The frontend is complete: create, list view with items, publish toggle, browse published
lists, and an owner-only history panel. Seven frontend tests, mutation-verified -- including
two that exist specifically because the first four could not see the loader's `isSelf` gate.

Then `scripts/verify-lists-live.sh` queried the RUNNING server and found two defects that a
fully green suite had shipped:

1. **`auditTrail.actor` was always null.** `listAuditToModel` built the model with ID,
   Action and CreatedAt and nothing set Actor. The field is nullable and documented as "or
   null if that account no longer exists", so every row reported null and the frontend's
   "a former member" branch rendered for publications that plainly had an owner.
   The unit tests had passed a nil actor in, so they agreed with the bug.
2. **`auditTrail.action` was `publish` where the schema declares `ListAuditActionEnum`.**
   The column stores the lower-case verb; the resolver cast the raw string; gqlgen serialised
   it verbatim. `TestListPublishAndAddItemRoundTripTheirEnums` asserts on `entityType` and
   never looks at `auditTrail.action` -- the test named "round trip their enums" was
   checking one of the two enums.

Both now have regression tests in `list_audit_actor_integration_test.go`, both
mutation-verified. The enum test asserts ENUM MEMBERSHIP rather than a literal, because a
literal pins today's value while membership is the property the schema promises.

### A design contradiction in migration 107, for the owner to decide

Two foreign keys disagree, and the consequence is that a documented behaviour is unreachable:

```
list_audit.list_id  ON DELETE CASCADE   -> delete the owner, delete the list
list_audit.actor_id ON DELETE SET NULL  -> ...which deletes the trail before SET NULL runs
```

The actor of a publish is the owner by construction -- only the owner may publish. So the
only way to null an `actor_id` is to delete the owner, and that cascades the list and its
whole trail. **A row can never be observed with `actor_id IS NULL`.** The nullable field,
the "or null if that account no longer exists" wording, and the "a former member" UI are all
dead code by construction. No test could have reported this: every test that tried would have
deleted the list's owner, which takes the trail with it.

Two fixes, both product decisions, so neither is made here:

1. `lists.owner_id ON DELETE SET NULL` as well, treating an ownerless list as undeletable.
   Larger blast radius -- every ownership check must handle a null owner.
2. Drop the "or null" wording and render nothing for a missing actor, accepting that the
   column is nullable only so the FK can be `SET NULL` on a row that never renders.

`TestAuditTrailIsDeletedWithItsListBecauseTheActorIsTheOwner` pins current
behaviour with the reasoning in the failure message, so the next reader sees why rather than
assuming a bug.

### One decision to flag for the frontend

`listCreate` requires READ, not MODIFY. Creating a private list harms nobody and is the
cheapest way to get a list onto the instance; requiring MODIFY puts a wall in front of it
for no gain. `listPublish`, `listDelete` and every item mutation require MODIFY. If you
would rather gate creation too, it is a one-word change in
`graphql/schema/types/list.graphql` plus a re-run of `go generate ./internal/models/`.
